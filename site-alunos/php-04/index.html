Até a L3 os dados moravam num array dentro do código: reiniciou, sumiu. Um banco de dados guarda os dados de verdade, organizados em tabelas: cada coluna é um campo (nome, horas) e cada linha é um registro (um curso). A língua para conversar com o banco é o SQL: create table, insert, select. O playground tem um banco SQLite de verdade, que nasce vazio a cada execução. Repare nos ?: o valor vai separado do SQL, e é isso que protege contra SQL injection. No fim, o mesmo select com o Query Builder do Laravel, sem escrever SQL.

  
Experimente: insira o curso JavaScript com 12 horas e mude o where horas >= ? para mostrar só os cursos com menos de 12 horas.







  
No Laravel ninguém cria tabela com SQL na mão: a gente escreve uma migration, um arquivo PHP em database/migrations que descreve a tabela. Ela tem dois métodos: up() (o que fazer) e down() (como desfazer). Dentro do Schema::create, cada linha $table->... é uma coluna. Quem roda as migrations é o comando php artisan migrate; aqui, artisan("migrate"). O Laravel anota numa tabela chamada migrations o que já rodou: rodar de novo não repete nada. É assim que toda a equipe (e o servidor) chega no mesmo banco.

  
Experimente: acrescente $table->string("professor"); na migration e rode de novo: a coluna nova aparece na lista.







  
Cada coluna tem um tipo: string (texto curto), text (texto longo), integer, decimal (dinheiro), boolean, date, enum (uma lista fechada de opções). Depois do tipo vêm os modificadores: ->nullable() deixa a coluna ficar vazia (NULL); ->default(0) dá um valor quando ninguém manda; ->unique() proíbe repetir. Sem modificador, a coluna é obrigatória. O migrate --pretend mostra o SQL que o Laravel vai mandar, sem rodar nada.

  
Experimente: insira um terceiro aluno com o e-mail da Ana. Leia o erro: UNIQUE constraint failed. Depois tire o "mensalidade" de um insert e veja o NOT NULL constraint failed.







  
A tabela já está no ar e agora precisa de uma coluna nova. Não edite a migration antiga (no banco dos colegas e do servidor ela já rodou e não roda de novo): crie uma migration nova com Schema::table, que altera uma tabela existente. Como já existem alunos, a coluna nova precisa ser ->nullable() ou ter um ->default(). Errou? migrate:rollback roda o down() do último lote e desfaz. O migrate:status mostra o que já rodou (Ran) e o que falta (Pending).

O Eloquent é o jeito do Laravel conversar com o banco usando classes (a L2 valendo a pena!). Cada tabela ganha um Model em app/Models: a classe Curso cuida da tabela cursos, e cada objeto Curso é uma linha. Com ele, Curso::create([...]) faz o INSERT, Curso::all() traz todas as linhas e Curso::find(3) busca pelo id. As colunas viram propriedades: $curso->nome. O $fillable diz quais colunas o create() pode preencher (exemplo 08). O nome da tabela é o da classe no plural, em inglês: Curso → cursos funciona, mas Professor → professors. Nesse caso, diga o nome certo com protected $table = "professores";.

  
Experimente: troque o echo do Curso::find(3) por dump(Curso::find(3)); para ver o objeto inteiro, com created_at e updated_at preenchidos sozinhos.







  
O where filtra as linhas: Aluno::where("media", ">=", 7). Sem o operador, vale o =. Dá para encadear: dois where são "e"; orWhere é "ou". Depois vêm orderBy (ordem), take (só os N primeiros) e o método que executa a consulta: get() (a lista), first() (o primeiro ou null), count(), avg(), max() ou pluck("nome") (só uma coluna). Enquanto não chega nesse último método, nada foi ao banco: é só um SQL sendo montado (o toSql() mostra qual).

  
Experimente: mostre os alunos da manhã em ordem alfabética, e quantos estão em recuperação (média de 5 até 7) com dois where.







  
Para alterar uma linha: busque o objeto, mude a propriedade e chame save(); ou use update([...]), que muda e salva de uma vez. O Eloquent só manda para o banco as colunas que mudaram, e atualiza o updated_at sozinho. Para apagar: $tarefa->delete(), ou Tarefa::destroy(3) direto pelo id. Um where(...)->update([...]) ou where(...)->delete() mexe em várias linhas com um comando só. Cuidado: sem where, mexe em todas! O $casts converte a coluna quando ela sai do banco: feita volta como true/false, não 1/0.

  
Experimente: marque todas as tarefas como feitas com um comando: Tarefa::where("feita", false)->update(["feita" => true]);.







  
O create($dados) é perigoso se os dados vêm direto de um formulário: alguém pode acrescentar admin=1 no HTML e virar administrador. Esse ataque se chama mass assignment. Por isso o Laravel bloqueia tudo até você listar no $fillable o que o create()/update() pode preencher. O que estiver fora da lista é ignorado sem aviso, então vale conferir quando um campo "não salva". Colunas sensíveis (como admin) você preenche de propósito, uma por uma: $usuario->admin = true;. Existe o contrário, $guarded = [] (libera tudo), mas use com cuidado.

  
Experimente: acrescente "admin" ao $fillable do Usuario e rode: o hacker vira admin. Por isso ela não deve estar lá.







  
Toda vez que alguém instala o projeto, o banco começa vazio. Um seeder (de seed, semente) é uma classe em database/seeders com um método run() que cadastra dados iniciais: os cursos, um usuário de teste. O DatabaseSeeder é o principal e chama os outros com $this->call(...). Rode com php artisan db:seed. No seu computador, migrate:fresh --seed apaga todas as tabelas, roda as migrations do zero e semeia de novo: ótimo para recomeçar limpo, proibido em produção (apaga os dados reais).

  
Experimente: crie um AlunoSeeder (com a migration e o model) e coloque no call([CursoSeeder::class, AlunoSeeder::class]).







  
Um curso tem muitas aulas; uma aula pertence a um curso. No banco, quem guarda essa ligação é a chave estrangeira: a coluna curso_id na tabela aulas, criada com foreignId("curso_id")->constrained(). O banco recusa um curso_id que não existe, e o cascadeOnDelete() apaga as aulas junto com o curso. No Model, cada lado vira um método: hasMany(Aula::class) no Curso e belongsTo(Curso::class) na Aula. Repare na diferença: $curso->aulas (sem parênteses) é a lista pronta; $curso->aulas() (com parênteses) é uma consulta para continuar (->where, ->count(), ->create()).

  
Experimente: cadastre o curso CSS com duas aulas pelo $css->aulas()->create(...) e mostre "A aula X é do curso Y" para uma delas.







  
O Eloquent escreve o SQL por você, mas vale espiar: o DB::listen roda uma função a cada consulta que vai para o banco. Repare na primeira listagem: uma consulta para os cursos e mais uma para cada curso (as aulas dele). Com 3 cursos são 4 consultas; com 500 cursos, 501. Esse é o famoso problema N+1, a causa mais comum de página lenta em Laravel. A correção é avisar antes que você vai usar as aulas: Curso::with("aulas")->get() busca as aulas de todos os cursos numa consulta só. São 2 consultas, não importa quantos cursos existam.

  
Experimente: cadastre mais 3 cursos no laço do começo (mude o array) e compare de novo o total de consultas com e sem with.







  
O site da escola da L3, agora com os cursos vindo do banco: migrations criam as tabelas, um seeder cadastra os cursos e as aulas, os Models fazem as consultas e o controller entrega para as views em Blade. Repare no findOrFail($id): se o curso não existe, o Laravel responde 404 sozinho, sem precisar do if com abort(404) da L3. E o with("aulas") já evita o N+1 na lista. Clique em 🌐 ver como página para ver o HTML.

  
Experimente: no seeder, crie o curso JavaScript sem aulas e visite a página dele: o @forelse mostra "Aulas em breve".
